# 4. Trivy replaces OWASP Dependency-Check as the dependency CVE scanner

Date: 2026-08-28

## Status

Accepted. Supersedes the dependency-scanning portion of the original quality-gate
specification, which named OWASP Dependency-Check.

## Context

The first real CI run failed in the `dependency_check` stage:

```
[ERROR] Failed to execute goal org.owasp:dependency-check-maven:9.0.10:check
[ERROR] ... MojoExecutionException
```

This was a `MojoExecutionException`, not a `MojoFailureException` — the plugin
**errored**, it did not report vulnerabilities. Dependency-Check 9.x builds a local
copy of the NVD CVE database on first run through the NVD 2.0 REST API. That API is
rate-limited to roughly 5 requests per 30 seconds for anonymous callers (50 with an
API key), and the initial population is thousands of paged requests. On a GitHub-hosted
runner — a shared, heavily-used egress IP — an unauthenticated run reliably receives
HTTP 403/429 and aborts before analysing a single dependency.

The remedy prescribed by the tool is an NVD API key, which NIST issues to an email
address on request. That key cannot be generated by the build; it requires a human to
register and then supply it as a repository secret, and it becomes a permanent
operational dependency (keys can be revoked, and the NVD database download remains the
slowest stage in the pipeline even when authenticated).

Trivy is already installed and passing in two stages of this pipeline (`trivy_fs`,
`trivy_image`). It ships its own vulnerability database, sourced from the same upstream
advisory feeds (NVD, GitHub Security Advisories, and per-ecosystem sources), requires no
API key, and is not subject to per-caller rate limiting.

## Decision

Remove OWASP Dependency-Check and scan Java dependencies with Trivy instead.

The scan target is the **built Spring Boot JAR**, not the source tree. This distinction
is the whole substance of the decision:

- `trivy fs .` over the repository sees `pom.xml`, from which Trivy cannot resolve the
  transitive dependency graph. It would report almost nothing and appear green.
- `trivy rootfs`/`trivy fs` over `target/*.jar` inspects the fat JAR's `BOOT-INF/lib/`,
  where every resolved dependency — direct and transitive — is present as a concrete
  versioned artifact. This is the equivalent of what Dependency-Check analysed.

The `dependency_check` stage is therefore replaced by a `dependency_scan` stage that
downloads the `app-jar` artifact produced by `build` and scans it.

Gate severity is unchanged in substance: Dependency-Check failed on CVSS >= 7.0, which
is the High/Critical band. Trivy is configured with `--severity CRITICAL,HIGH`, giving
the same threshold expressed in the tool's own vocabulary.

`--ignore-unfixed` is deliberately **not** set on this stage, unlike the filesystem and
container scans. On a base OS image an unfixable CVE is noise the maintainer cannot act
on; in an application's own dependency set it is a genuine finding that should be
visible even if it currently has no upstream patch.

## Consequences

Positive:

- No API key, no external account, no rate-limited database download. The stage is
  self-contained and reproducible.
- Substantially faster: no multi-thousand-request NVD population on a cold cache.
- One fewer scanner to keep configured; Trivy's DB is already being fetched by two
  other stages in the same run.

Negative / accepted:

- The CVE-to-artifact matching differs. Dependency-Check uses CPE heuristics and is
  known for false positives; Trivy matches on package coordinates from the JAR, which
  is more precise but will not flag a vulnerability whose advisory is missing from
  Trivy's feed. Neither tool is a superset of the other.
- The suppression mechanism changes. `config/owasp/suppressions.xml` is removed; Trivy
  uses `.trivyignore`. That file is created with **no entries**, and the same policy
  applies as before: an entry requires a written justification of why the CVE does not
  apply to this application, not "we will fix it later".
- SBOM generation is unaffected — it is produced by the CycloneDX Maven plugin in the
  separate `sbom` stage and never depended on Dependency-Check.

## Alternatives considered

**Obtain an NVD API key and keep Dependency-Check.** Rejected here only because it
requires a human registration step outside the build and adds a revocable external
credential to the critical path of every deploy. It remains a legitimate choice; the
plugin configuration was working, and reinstating it means restoring the plugin block,
the stage, and setting `NVD_API_KEY`.

**Lower `failBuildOnCVSS` or add `continue-on-error`.** Rejected outright. The stage was
not reporting vulnerabilities — it was erroring — so suppressing the failure would have
disabled dependency scanning entirely while presenting a green gate.
